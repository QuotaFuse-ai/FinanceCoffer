# DEC-0029 公开文档卫生检查由提交前钩子执行

- 日期：2026-10-31
- 状态：已采纳
- 关联：`DEC-0025`（判定口径）、`DEC-0026`（内部过程材料只留本地）、`tools/check_public_docs.py`、`.pre-commit-config.yaml`、`tests/unit/test_public_docs.py`、`README.md` 第 10 节

## 背景

DEC-0025 第 5 条要求「规则由机器兜底」，但一直没落地：规则只写在决策里，靠人记住，已经漏过一次。缺的是一件能挡住下一次提交的工具，而不是一份更详细的说明。

四类内容里，前三类（内部任务编号、团队称谓、本机绝对路径）有明确的字面特征，可以正则判定；第四类（客户名 / 真实机构名）没有自动化判据——「哪些名字算客户名」只有人知道，用启发式猜测会把产品名、数据源名误判成违规。

执行点有两个候选：提交前钩子，或者持续集成里单开一个 step。当前分支没有 CI 描述文件（主流水线在主干上），在此重建一份会与之长期冲突；而本机已有可用的钩子管理工具。

## 决策

1. **检查逻辑集中在一个脚本** `tools/check_public_docs.py`：扫描 `docs/`、`deploy/` 与根 `README.md`，命中即非零退出，逐行打印 `文件:行: 命中原因`。规则表、词表、豁免路径都是脚本内的常量，追加一条不需要改动扫描逻辑。

2. **四类规则都建了槽位，第四类留空名单。** 客户名 / 真实机构名保留规则与接线（名单非空即生效），暂不放判据；单测覆盖「空名单不命中、名单补上即命中」。

3. **豁免按路径前缀实现，只有 `docs/decisions/`。** 依据 DEC-0025 第 4 条，决策记录只增不改，其中的历史写法一律保留原样。豁免由脚本内的前缀表决定，不提供行内注释、标记之类的绕过方式——绕过一旦可用，就会有人在正文里用它躲检查。

4. **执行点选提交前钩子**：`.pre-commit-config.yaml` 注册 `local` + `language: system` 的单个钩子，`always_run` 且不带文件名（脚本自己决定扫描范围，才能正确处理豁免目录）。安装是一次性的 `pre-commit install`，复检是 `pre-commit run public-docs --all-files`。

5. **主干的持续集成流水线合入后，再补一个 step 调用同一个脚本**。钩子可以被 `--no-verify` 跳过，CI 不行；两个执行点跑同一份脚本没有额外维护成本。在那之前，`tests/unit/test_public_docs.py` 里有一条「当前检出公开面必须通过检查」的基线用例，它随既有的 pytest 步骤运行，等于暂时补上了 CI 这一道。

6. **词表只收组织称谓，不收行业通用职能词**（按 DEC-0025 第 3 条）：描述工具类别、使用人身份或表名释义的通用词保留原词；外部协作方的「XX 团队」写法由一条通用规则兜住，不误伤正文里对规则本身的表述。

## 权衡

- **为什么不选 CI 作为唯一执行点**：当前分支不含流水线描述文件，新建即与主干版本对撞；而且违规要等到推送之后才报出来，成本高于在提交时就拦下。
- **钩子的已知弱点**：`--no-verify` 能跳过，未安装钩子的检出不会自动检查。用第 5 条的 pytest 基线用例对冲，并在 README 里写明安装与复检命令。
- **为什么每次跑全量而不是只看暂存文件**：公开面体量小（百余个文本文件，全量毫秒级），而「只看改动文件」会漏掉跨文件引用与新写入的旧目录文件；范围收窄换来的加速不值这点风险。
- **为什么 `ruanjian` 这类目录名单独列一条**：它是本机解释器目录的名字，不含盘符也不像 Unix 绝对路径的通用形态，靠通用规则抓不到。
- **代价**：`工程师`、`架构师` 等词进了词表，正文里指代职能时可能需要同步改写。可接受——需要改写的位置本来就是「谁来做」的表述。
